# Surrogate Keys in Iceberg Tables

A surrogate key (SK) is a key generated by the warehouse, such as `customer_sk` 1, 2, 3, kept next to
the natural key from the source (`custkey`). In SQL databases it is usually an identity column
(`GENERATED BY DEFAULT AS IDENTITY`). This note shows how to get the same result in Iceberg tables
written by Spark.

## 1. The Problem

Iceberg has no identity or auto-increment column. The table spec defines default values
(`initial-default`, `write-default`) but no sequence, and the request to add identity columns
(issue #12297) was closed without being implemented. The SK is therefore declared as an ordinary
column, and the load job fills it in:

```sql
CREATE TABLE IF NOT EXISTS lake.gold.dim_customer (
  customer_sk bigint NOT NULL,   -- surrogate key, filled in by the load job
  custkey     bigint NOT NULL,   -- natural key (source)
  name string, address string, mktsegment string,
  _loaded_at timestamp)
USING iceberg;
```

## 2. The Rule

Each run of the load job:

1. **Existing natural key** (already in the dimension): reuses its SK, found by a join with the
   dimension.
2. **New natural key:** gets `max(existing SK) + row_number()`, numbered over the new keys only.
3. **Rerun:** every key now exists, so nothing is renumbered; the run is idempotent.

On the first run the dimension is empty: `max` is null, `coalesce(..., 0)` makes it 0, and the SKs
start at 1.

The SK comes from the join and the numbering, not from the write. That is why the same rule works
with `MERGE INTO` ([3](#3-with-merge-into)) and with a full rebuild ([4](#4-with-a-full-rebuild)).

## 3. With `MERGE INTO`

Use it for an incremental load: existing keys are updated, new keys are inserted.

The source is the current state of each customer, one row per `custkey`, here a temporary view built
from silver (latest `updated_at` per key):

```sql
CREATE OR REPLACE TEMP VIEW silver_customer_current AS
SELECT custkey, name, address, mktsegment
FROM (SELECT *, row_number() OVER (PARTITION BY custkey ORDER BY updated_at DESC) AS rn
      FROM lake.silver.customer)
WHERE rn = 1;
```

The merge:

```sql
MERGE INTO lake.gold.dim_customer t
USING (
  SELECT s.*,
         coalesce(d.customer_sk,                                  -- 1. existing key: keeps its SK
                  m.max_sk + row_number() OVER (                  -- 2. new key: max + 1, 2, ...
                    PARTITION BY d.customer_sk IS NULL ORDER BY s.custkey)) AS customer_sk
  FROM silver_customer_current s
  LEFT JOIN lake.gold.dim_customer d ON d.custkey = s.custkey
  CROSS JOIN (SELECT coalesce(max(customer_sk), 0) AS max_sk FROM lake.gold.dim_customer) m
) s
ON t.custkey = s.custkey
WHEN MATCHED THEN UPDATE SET
  name = s.name, address = s.address, mktsegment = s.mktsegment, _loaded_at = current_timestamp()
WHEN NOT MATCHED THEN INSERT (customer_sk, custkey, name, address, mktsegment, _loaded_at)
  VALUES (s.customer_sk, s.custkey, s.name, s.address, s.mktsegment, current_timestamp());
```

Clause by clause:

| Clause | What it does |
|---|---|
| `LEFT JOIN lake.gold.dim_customer d` | Finds the SK of keys already in the dimension; `d.customer_sk` is null for new keys |
| `CROSS JOIN (... max(customer_sk) ...) m` | Reads the highest SK once, before any change |
| `PARTITION BY d.customer_sk IS NULL` | `row_number()` counts new keys and existing keys separately, so only the new keys use numbers and the sequence has no gaps |
| `ORDER BY s.custkey` | Makes the numbering of a run repeatable: the same new keys get the same numbers |
| `coalesce(d.customer_sk, ...)` | Existing key: its SK; new key: `max + n` |
| `WHEN MATCHED THEN UPDATE` | Updates the attributes and never `customer_sk`, so an SK never changes |
| `WHEN NOT MATCHED THEN INSERT` | Inserts the new key with its new SK |

`MERGE INTO` needs the Iceberg Spark extensions
(`spark.sql.extensions: org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions`), already
set in the project's `SparkApplication` files.

## 4. With a Full Rebuild

Use it for a small dimension rewritten in every run. The same join and numbering produce the SKs,
then one statement replaces every row:

```sql
INSERT OVERWRITE lake.gold.dim_customer
SELECT coalesce(d.customer_sk,
                m.max_sk + row_number() OVER (
                  PARTITION BY d.customer_sk IS NULL ORDER BY s.custkey)) AS customer_sk,
       s.custkey, s.name, s.address, s.mktsegment, current_timestamp() AS _loaded_at
FROM silver_customer_current s
LEFT JOIN lake.gold.dim_customer d ON d.custkey = s.custkey
CROSS JOIN (SELECT coalesce(max(customer_sk), 0) AS max_sk FROM lake.gold.dim_customer) m;
```

The `SELECT` reads the table as it was before the write, so existing keys keep their SK even though
every row is rewritten. Without a `PARTITION` clause, `INSERT OVERWRITE` replaces all rows of an
unpartitioned table, and Iceberg overwrites are atomic: one commit, all or nothing.

## 5. In the Fact Table

The fact table generates no SK. It looks up each dimension's SK by the natural key and stores it:

```sql
SELECT c.customer_sk, l.orderkey, l.linenumber, l.quantity, l.extendedprice
FROM silver_lineitem_current l
JOIN silver_orders_current o ON o.orderkey = l.orderkey
LEFT JOIN lake.gold.dim_customer c ON c.custkey = o.custkey;
```

Load the dimensions before the facts, so every natural key already has its SK. With a `LEFT JOIN`, a
fact whose key is missing from the dimension gets a null SK instead of being dropped; it shows the
gap instead of hiding it.

## 6. Conditions

- **One writer per dimension at a time.** Two jobs running together would read the same `max` and
  hand out the same numbers. Run the dimension load as a single job, before the facts.
- **The natural key must be unique in the source.** The source view keeps one row per key; with
  duplicates, one key would get two SKs.
- **Never update the SK.** It is assigned once, at insert.

## 7. Why Not `_row_id`

From format v3 on, Iceberg gives every row a hidden `_row_id` column (row lineage). The spec defines
it as "a unique long identifier for every row within the table", assigned when the row is first added
(the data file's `first_row_id` plus the row's position in the file), from a table counter
`next-row-id`. When a row only moves to another file (compaction, update), the engine must keep its
`_row_id`.

It does not work as an SK:

- **It belongs to the row, not to the natural key.** A row deleted and inserted again is a new row
  with a new `_row_id`. A batch overwrite or a full rebuild ([4](#4-with-a-full-rebuild)) does exactly
  that, so the facts would point to IDs that no longer exist. Updates through equality deletes also
  get a new ID.
- **It has gaps.** Ranges are reserved per manifest and data file, including for existing rows.
- **It is known only after the commit.** Copying it into an SK column needs a second write, and the
  frozen copy is then the sequence of [2](#2-the-rule) with gaps and more steps.
- **It needs format v3**, supported by every engine that reads the table. The default
  `format-version` of a new table is 2 (since Iceberg 1.4.0), and the project's tables do not change
  it.
- **Its purpose is lineage:** tracking a row across changes, not identifying a business entity.
