# 02 — Transactional Ingestion: TPC-H in Postgres, Cursor and CDC: Plan

Status: Draft

## Objective

Simulate a transactional database (TPC-H with event dates moved to the present) and ingest it with
Airbyte into the S3 bronze bucket in two ways: incremental by a date column, and incremental by CDC.
DuckDB generates the data and reads both the source Postgres and the Parquet files in bronze. The
phase is delivered as three labs: lab01 (API, from phase 01), lab02 (date cursor) and lab03 (CDC).

## Scope

- Source Postgres in the cluster, with logical replication (`wal_level=logical`)
- DuckDB as a permanent service in the cluster (Quack), reading the source Postgres and the bronze
  bucket (IRSA)
- TPC-H generated by DuckDB, scale factor chosen at load time (SF0.1 or SF1)
- Two schemas in Postgres: the original TPC-H (as generated) and a transactional one used as the
  operational system
- Dates shifted once at load time, so the latest date is the load day minus one day
- `customer` in the transactional schema gets `start_at` = date of its first purchase; customers
  that never bought stay only in the original schema
- A day-simulation script: inserts, updates and deletes for a given simulated day
- CDC preparation in the source: publication, replication slot, replication user
- lab02 and lab03 built in the Airbyte UI, not saved
  ([D-021](../../docs/decisions/021-airbyte-connection-ui-lab.md)); lab01 reused from
  [phase 01](../01-ingestion-airbyte-s3/lab01-api-ingestion.md)

## Out of Scope

- Trino, dbt, Airflow
- Saving the Airbyte configuration (D-021)
- Sync scheduling
- Azure and GCP deployments
- High availability and backups of the source database
- Deduplication: the Airbyte S3 destination does not support "Incremental Append + Deduped", so the
  labs use "Incremental Append"

## Done When

- Following the phase README, the source Postgres, the DuckDB service and the TPC-H data come up on
  the phase 01 environment
- lab02: after a simulated day, an incremental sync by date column brings that day's records into
  bronze (which changes it captures depends on open point 3)
- lab03: after a simulated day, a CDC sync brings that day's inserts, updates and deletes into bronze
- DuckDB reads the source Postgres and the Parquet files in bronze
- The teardown removes every resource that incurs cost
- No secrets in the repository

## Decisions

Answered so far; the ADRs are written when the plan is approved.

| # | Decision | Answer |
|---|---|---|
| D-022 | Where the source Postgres runs | Plain StatefulSet (official `postgres` image) in the cluster; the reason is still to be recorded |
| D-023 | DuckDB as a service | Quack (official DuckDB client-server protocol) |
| D-024 | Dataset and scale | TPC-H; scale factor as a parameter, SF0.1 or SF1 (size resources for SF1) |
| D-025 | Event date control | Shift every date once at load time (latest = load day − 1); `customer.start_at` = first purchase; reference tables (`region`, `nation`, `supplier`, `part`, `partsupp`) have no date and use full refresh |

## Open Points

1. Reason for D-022 (plain StatefulSet instead of the recommended RDS).
2. Schema names (e.g., `tpch` and `sales`).
3. lab02 cursor: business dates only (`o_orderdate`, `l_shipdate`, `start_at`), which capture inserts
   only, or also an `updated_at` on `orders` and `lineitem`, which also captures updates.
4. Whether the original schema is the reservoir from which the simulation inserts never-buying
   customers into the transactional schema on their first simulated purchase.
5. Whether the date shift applies to the original schema too, or only to the transactional one.
6. D-026: which rows the simulation updates and deletes (oldest first, random, or a date window).
7. Upsert and delete method: native Postgres SQL through `postgres_execute`, DuckDB SQL on the
   attached tables, or `MERGE`; and deletes with a foreign key plus explicit delete, with
   `ON DELETE CASCADE`, or without a foreign key.
8. D-027: where scripts and labs live.

**Divergences to resolve (principle 7):** README §3 lists phase 02 as Trino and dbt (this phase
becomes 02; Trino/dbt 03; Airflow 04), and README §2 does not list DuckDB or a source database.
Both updates belong to step 02.01.
